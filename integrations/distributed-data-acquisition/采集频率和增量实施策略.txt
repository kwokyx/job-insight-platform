## 标题
为分布式采集模块补齐新增入库字段、定时采集频率与增量采集闭环

## Summary
本次改造只覆盖分布式采集模块本身，并给出需要前后端配合的接口与字段契约。目标是实现三件事：

- 扩展职位入库字段，允许当前搜索接口取不到的字段先为空，后续再补详情抓取
- 在调度中心实现真正可运行的定时采集：默认每天 `00:00` 执行，并支持用户自定义“简单频率 + 时间”
- 将现有“主键去重 + 重复更新”升级为真正可执行的增量策略：增量任务只抓少量前页，复用历史水位线，并在无新增时提前停止

默认方案：
- 新增字段全部入库、全部允许为空
- 前端对外暴露“简单频率 + 时间”，后端内部统一转换为 cron 表达式
- 默认新建定时任务为“每天 00:00”
- 增量策略优先服务智联招聘，其他渠道先复用同一套调度与入库框架

## Key Changes

### 1. 扩展职位入库字段与消息结构
在 `job_data` 模型、初始化 SQL、消息 schema、爬虫解析结果中统一增加以下字段，全部可空：
- `district`
- `street_name`
- `requirements`
- `address`
- `company_type`
- `industry_name`
- `industry_code`
- `company_url`
- `job_skill_tags`
- `job_keywords`

实现要求：
- `job_skill_tags` 保存原始技能标签，建议用 `TEXT` 存逗号拼接或 JSON 字符串，和现有 `job_labels` 保持风格一致
- `job_keywords` 为合并去重后的关键词标签，来源优先级为 `jobSkillTags + jobLabels + 搜索关键词`
- 当前 `search/positions` 能拿到的字段直接解析入库；无法稳定拿到的字段写空，不阻塞本次改造
- `requirements` 与 `position_info` 分离：`position_info` 保留岗位描述整体文本，`requirements` 优先放任职要求片段；若搜索接口无法区分则先留空
- `company_type` 不替换现有 `company_finance`；前者表示企业性质，后者继续表示融资/类型信息
- `industry_name`/`industry_code` 若搜索接口缺失则置空，不做猜测映射

需要调整的接口/类型：
- `scheduler-center/app/models/task.py` 的 `JobData`
- `deploy/init.sql` 的 `job_data`
- `scheduler-center/app/schemas/task.py` 的 `JobDataMessage`
- `crawler-node/core/spider/zhaopin_spider.py` 的职位解析结果
- `scheduler-center/app/mq/consumer.py` 的字段级 upsert 比对列表

### 2. 任务模型补齐“定时 + 增量”元数据
在 `crawl_task` 增加以下字段并同步到 ORM / SQL / API：
- `schedule_type`：`IMMEDIATE` / `SCHEDULED_TEMPLATE` / `SCHEDULED_RUN`
- `cron_expression`
- `incremental`
- `baseline_task_id`
- `incremental_page_limit`
- `stale_page_threshold`
- `lookback_hours`
- `last_success_at`
- `watermark_publish_date`
- `watermark_crawl_time`
- `schedule_timezone`
- `schedule_enabled`
- `next_run_time`
- `last_run_time`

在 `crawl_task_shard` 增加：
- `stop_reason`
- `new_count`
- `updated_count`
- `duplicate_count`

默认值：
- `schedule_type="IMMEDIATE"`
- `incremental=false`
- `incremental_page_limit=2`
- `stale_page_threshold=2`
- `lookback_hours=72`
- `schedule_timezone="Asia/Shanghai"`
- `schedule_enabled=true`

语义约定：
- `SCHEDULED_TEMPLATE` 是定时模板任务，不直接执行采集
- `SCHEDULED_RUN` 是由模板派生出来的真实执行子任务
- `IMMEDIATE` 是手动立即执行任务

### 3. 任务创建、启动与拆分策略改为“模板任务 + 执行任务”
调整 `TaskCreate` 和 `TaskResponse`，新增以下对外字段：
- `incremental`
- `baseline_task_id`
- `schedule_type`
- `cron_expression`
- `schedule_enabled`
- `schedule_timezone`
- `schedule_preset`
- `schedule_time`
- `schedule_days`
- `incremental_page_limit`
- `stale_page_threshold`
- `lookback_hours`
- `last_success_at`
- `watermark_publish_date`
- `watermark_crawl_time`
- `next_run_time`
- `last_run_time`

后端对外支持两种提交方式，但内部统一转 cron：
- 简单计划字段：
  - `schedule_preset`: `DAILY` / `WEEKLY` / `MONTHLY`
  - `schedule_time`: `HH:mm`
  - `schedule_days`: 周几或每月几号
- `cron_expression`：后端内部持久化字段，前端默认不直接编辑

创建逻辑：
- `IMMEDIATE`：创建后照旧拆分分片，手动启动或立即执行
- `SCHEDULED_TEMPLATE`：只保存模板，不立即拆分
- 若未传定时信息但选择定时任务，默认生成“每天 00:00”的 cron

增量基线逻辑：
- 若传 `baseline_task_id`，直接使用
- 若 `incremental=true` 且未传基线，自动找同渠道、同关键词/城市配置、最近一次成功任务
- 若找不到基线，创建“冷启动增量任务”，仍按增量页数运行，但不使用旧水位提前停页

拆分逻辑：
- 全量任务：继续使用 `page_count`
- 增量任务：使用 `incremental_page_limit`，每个维度组合只拆前 `N` 页
- 分片消息新增：
  - `incremental`
  - `baseline_task_id`
  - `watermark_publish_date`
  - `watermark_crawl_time`
  - `stale_page_threshold`
  - `lookback_hours`
  - `search_keyword`，用于生成 `job_keywords`

### 4. 调度中心增加真正的定时执行器
在 `scheduler-center/app/main.py` 启动流程中增加轻量调度器，推荐 APScheduler 或单进程后台扫描线程；本次以单实例部署为前提，不做分布式抢占。

执行器职责：
- 定期扫描 `schedule_type='SCHEDULED_TEMPLATE' and schedule_enabled=true and next_run_time <= now`
- 为每个到点模板生成一条 `SCHEDULED_RUN` 子任务
- 子任务复制模板的关键词、城市、渠道、页数、增量配置
- 子任务 `parent_task_id=模板任务ID`
- 子任务 `baseline_task_id=模板最近一次成功执行任务或自动选出的最近成功任务`
- 生成后立即走现有 `process_task + start_task` 流程
- 模板自身不直接进入运行态，只更新 `last_run_time` 和下一次 `next_run_time`

时间规则：
- 默认按 `Asia/Shanghai`
- “每天 00:00”转换为 `0 0 * * *`
- “每周/每月”也统一转换为 cron 存库
- 自定义时间必须校验合法性，非法输入在 API 层返回 400

### 5. Worker 与 Spider 实现增量判定和提前停页
扩展 `TaskShardMessage`、worker 调用链和 `ZhaopinSpider.crawl()` 入参，接收增量上下文。

判定规则：
- `publish_date` 为空：不作为“旧页停止”依据
- `publish_date > watermark_publish_date`：记为新增候选
- `publish_date <= watermark_publish_date` 但最终库里不存在同 `url_obj_id`：仍记为新增候选
- 已存在且业务字段有变化：记为更新候选
- 已存在且无变化：记为旧/重复候选

页级停止策略：
- 当前页空结果：`stop_reason=NO_RESULTS`
- 当前页所有职位发布时间早于等于 `watermark_publish_date`：记为 stale page
- 当前页所有职位发布时间均落在 `lookback_hours` 之外，也记为 stale page
- 连续 stale pages 达到 `stale_page_threshold`：本地停止继续处理该维度组合的后续页
- 本次不做 RabbitMQ 队列中已投递后续分片的撤回；由 worker 本地跳过执行并正常回传完成结果，`stop_reason=ALL_OLD_PUBLISH_DATE` 或 `LOOKBACK_EXCEEDED`

实现方式：
- worker 维护一个进程内停止表，key 使用 `(task_id, keyword, city, category_code)`
- 一旦某页触发停止，后续同组分片进入队列时直接短路返回，不再请求智联接口
- 每个分片上报本页的 `new_count/updated_count/duplicate_count/stop_reason`

### 6. 调度中心入库层升级为“增量统计中心”
保留 `DataConsumer.save_job_data()` 的主键 upsert，但改为字段级比较更新。

关键比对字段：
- `title`
- `salary_min`
- `salary_max`
- `salary_raw`
- `job_city`
- `district`
- `street_name`
- `experience_year`
- `education_need`
- `publish_date`
- `job_welfare`
- `job_labels`
- `job_skill_tags`
- `job_keywords`
- `requirements`
- `position_info`
- `job_classification`
- `address`
- `company_name`
- `company_size`
- `company_type`
- `company_finance`
- `industry_name`
- `industry_code`
- `company_url`
- `company_logo`
- `url`

行为约定：
- 插入新职位：写 `crawl_time`，`crawl_update_time` 保持空，记新数据
- 已存在且字段有变化：更新字段，刷新 `crawl_update_time`
- 已存在且字段无变化：不覆盖业务字段，不改 `crawl_time`
- 统计归并到分片与任务：
  - `new_count`
  - `updated_count`
  - `duplicate_count`

任务完成时回写水位：
- 增量任务成功后更新 `last_success_at`
- 若本次存在更大的 `publish_date`，更新 `watermark_publish_date`
- 始终更新 `watermark_crawl_time=当前完成时间`
- 若本次没有新增，不回退 `watermark_publish_date`
- 全量任务成功后也写一次水位，供后续增量任务复用

## Frontend / Backend 对接清单

### 1. 需要前端传给采集模块的字段
创建/编辑任务接口需要新增以下请求字段：
- `incremental: boolean`
- `schedule_mode: "IMMEDIATE" | "SCHEDULED"`
- `schedule_preset: "DAILY" | "WEEKLY" | "MONTHLY"`
- `schedule_time: "HH:mm"`
- `schedule_days: string[] | number[] | null`
- `baseline_task_id: string | null`
- `incremental_page_limit: number`
- `stale_page_threshold: number`
- `lookback_hours: number`

前端默认值文案建议：
- “是否增量采集”：默认否
- “定时采集”：默认每天 00:00
- “增量采集页数”：默认 2 页
- “连续旧页停止阈值”：默认 2 页
- “发布时间回看范围”：默认 72 小时

### 2. 采集模块需要返回给前端的字段
任务列表/详情接口增加返回：

任务统计接口增加：
- `new_count`
- `updated_count`

分片详情接口增加：
- `stop_reason`
- `new_count`
- `updated_count`
- `duplicate_count`

### 3. 需要给前端同学的文字说明
前端侧需要知道：
- “立即执行”和“定时模板”是两类任务，定时模板不会直接进入运行中
- 定时模板每次触发会生成一个真实执行子任务
- “增量采集”不是只看发布时间；最终是否算新增仍以 `url_obj_id` 入库结果为准
- 部分字段如 `district/address/company_url/industry_code` 允许为空，这是当前采集接口能力限制，不代表接口异常

### 4. 需要给平台后端同学的接口说明
如果平台后端不是采集模块自身而是统一业务后端，则需要约定以下接口代理/转发字段：
- 创建任务：支持新增的调度与增量字段
- 查询任务列表/详情：透传新增返回字段
- 查询任务统计：透传 `new/updated/duplicate`
- 查询分片详情：透传 `stop_reason/new_count/updated_count/duplicate_count`

接口行为说明：
- 若 `schedule_mode="SCHEDULED"` 且未传时间，采集模块默认按每天 `00:00`
- 若 `incremental=true` 且 `baseline_task_id` 为空，采集模块自动选择最近成功基线
- 若找不到基线，不报错，按“冷启动增量”执行

## Test Plan
- `TaskCreate` 能正确保存新增字段，定时模板不会被立即拆分执行
- 立即任务仍按原流程创建、拆分、启动
- 定时模板到达 `next_run_time` 后能生成一次真实执行子任务
- 默认“每天 00:00”能正确转换为 cron 并计算下一次触发时间
- 增量任务只拆 `incremental_page_limit` 页，全量任务仍按 `page_count`
- 无基线时增量任务能冷启动执行
- `save_job_data()` 能正确区分新增、更新、重复
- `crawl_time` 不会因重复无变化数据被覆盖
- 新增字段能在入库、列表查询、消息消费链路中正确透传
- worker 在连续旧页达到阈值后能停止同组后续页
- 分片与任务统计能正确汇总 `new/updated/duplicate`
- 前端依赖的任务详情、统计、分片详情接口均能返回新增字段

## Assumptions
- 当前版本只在采集模块内完成调度、增量和入库改造，不负责业务平台主站前端页面实现
- 新增职位字段允许为空，不强制本次补详情页抓取
- 用户自定义定时对外采用“简单频率 + 时间”，不直接暴露 cron 编辑器
- 默认时区使用 `Asia/Shanghai`
- 默认每天 `00:00` 定时执行
- 默认不实现已投递 RabbitMQ 后续分片的撤回，只做 worker 本地跳过
- 采集模块仍以 `url_obj_id` 作为最终增量与去重兜底主键
